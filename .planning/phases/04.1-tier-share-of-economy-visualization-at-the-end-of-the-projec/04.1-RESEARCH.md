## Summary

Phase 4.1 adds VIZ-07: two new chart components (100%-stacked-area + end-of-horizon donut) that make wealth-share composition legible alongside the existing three charts. All the key engine primitives already exist — `cumulativeShareFromTop` in `src/core/distribution.ts` already computes wealth held above a percentile cut as a fraction of `totalWealth`; the five-band Lorenz mass decomposition is a set of five difference calls against that function at the four existing anchor percentile boundaries. The new computation belongs in a pure function in `src/core/tierBands.ts` that the planner creates, mirroring the `deriveShares` pattern in `relativePosition.ts`. A new memoized selector in `selectors.ts` maps `ProjectionResult → BandShareSeries` and builds the two ECharts option objects.

The ECharts patterns have one landmine worth documenting in detail: overlaying a `line` series on a `stack: '100%'` area requires placing the line series in the same `series[]` array as the stacked areas but with `stack` omitted and `yAxisIndex` pointing to a second hidden y-axis (0–100 percentile space). Without this, ECharts adds the line into the stack calculation and distorts the 100% normalization. The donut `emphasis` API uses `emphasis.itemStyle.borderColor` + `borderWidth` to outline the user's band slice — the old `selected` property is deprecated in ECharts 6 and does not apply to `pie` type.

The D-16 style-guide rule mirrors the D-15 rank-delta disclosure exactly: a verbatim caption template, a `<p>` DOM element on/near both charts, and a Phase 5 text-equality check. The caption formatter function follows `formatMoneyIllusionCaption` as the structural template — a pure framework-free function in a new `src/ui/shareFormatters.ts` (or inline in the selector) so Vitest can assert text equality without jsdom.

**Primary recommendation:** Implement `deriveBandShares` in `src/core/tierBands.ts` using `cumulativeShareFromTop` at the four anchor boundaries; add `selectShareOption` + `selectDonutOption` to `selectors.ts`; create `TierShareChart` and `DonutChart` in `src/viz/`; compose into AppShell following the existing `rawResult → null-guard → selector` chain; append D-16 to the style guide; add basis-invariance and band-sum-to-1 Vitest assertions.

## Pattern 1: Per-Band Lorenz Mass Integration

**What:** `deriveBandShares` takes the `series: YearSnapshot[]` from `ProjectionResult` and for each year computes the fraction of total wealth held by each of the 5 population bands by calling `cumulativeShareFromTop` at the four anchor boundaries.

**Math:** The five bands are defined by their CDF boundaries in population space:
- Bottom 50%: `[0, 0.5)` — wealth fraction = `1 - cumulativeShareFromTop(curve, 0.5)` = `1 - share_above_p50`
- 50–90%: `[0.5, 0.9)` — `cumulativeShareFromTop(curve, 0.5) - cumulativeShareFromTop(curve, 0.9)`
- 90–99%: `[0.9, 0.99)` — `cumulativeShareFromTop(curve, 0.9) - cumulativeShareFromTop(curve, 0.99)`
- 99–99.9%: `[0.99, 0.999)` — `cumulativeShareFromTop(curve, 0.99) - cumulativeShareFromTop(curve, 0.999)`
- Top 0.1%: `[0.999, 1]` — `cumulativeShareFromTop(curve, 0.999)`

These five values sum exactly to 1.0 by construction (they partition the total wealth).

**The fundamental challenge:** `YearSnapshot` carries `_totalWealth` (as an internal field) but does NOT carry the `Curve` object. `cumulativeShareFromTop` requires a `Curve`. Two options:

**Option A — Recompute curve from snapshot anchors:** Call `calibrateCurve` on each snapshot's `anchorWealth` at derivative-computation time. This is the clean, dependency-free approach. `calibrateCurve` is deterministic and cheap (sub-millisecond). The snapshot's `anchorWealth` values are exactly the anchor values the engine used to fit the curve for that year, so the reconstructed curve is correct.

**Option B — Extend YearSnapshot to carry band shares directly:** Have the engine compute band shares during the main loop and store them in the snapshot. This avoids reconstructing the curve but couples `tierBands` logic into `engine.ts`, which violates the separation-of-concerns pattern (engine loop vs. relativePosition.ts vs. the new tierBands.ts).

**Recommendation: Option A** — `deriveBandShares(series)` reconstructs the curve via `calibrateCurve(anchorWealthToAnchors(snap))` for each year. This mirrors how `deriveShares` works (it reads `_totalWealth` from the snapshot, but `deriveBandShares` needs the full curve for partial integrals). The engine team chose not to expose the Curve in the public result type deliberately; reconstructing it at the selector layer is the correct boundary crossing.

**Caveat on calibrateCurve fallback:** The engine itself falls back from `calibrateCurve` to `shiftScaleCurve` when calibration throws (evolved distribution edge case). `deriveBandShares` must mirror this: catch calibration errors and fall back to a `shiftScaleCurve`-derived curve. A `null` band share is preferable to a thrown error propagating into the selector layer.

**Alternative to calibrateCurve reconstruction:** Use a simplified closed-form derivation from `_totalWealth` and anchor values. However, `cumulativeShareFromTop` inherently requires the lognormal+Pareto curve parameters — there is no shortcut that avoids it. Option A is correct.

**Function signature (planned):**

```typescript
// src/core/tierBands.ts

export interface BandShare {
  year: number;
  bottom50: number;    // fraction ∈ [0,1] — population band [0, 0.5)
  band50to90: number;  // fraction ∈ [0,1] — population band [0.5, 0.9)
  band90to99: number;  // fraction ∈ [0,1] — population band [0.9, 0.99)
  band99to999: number; // fraction ∈ [0,1] — population band [0.99, 0.999)
  top01: number;       // fraction ∈ [0,1] — population band [0.999, 1]
}

export function deriveBandShares(series: YearSnapshot[]): BandShare[]
```

**Known fixture for tests:** For a pure Pareto(α=2, xm=1) distribution:
- `cumulativeShareFromTop(curve, p) = sqrt(1 - p)` (per `distribution.test.ts` known-Pareto fixture)
- Bottom 50%: `1 - sqrt(0.5) ≈ 0.2929`
- 50–90%: `sqrt(0.5) - sqrt(0.1) ≈ 0.7071 - 0.3162 ≈ 0.3909`
- 90–99%: `sqrt(0.1) - sqrt(0.01) ≈ 0.3162 - 0.1 ≈ 0.2162`
- 99–99.9%: `sqrt(0.01) - sqrt(0.001) ≈ 0.1 - 0.03162 ≈ 0.0684`
- Top 0.1%: `sqrt(0.001) ≈ 0.03162`
- Sum ≈ 1.0 ✓

This known fixture drives `tierBands.test.ts` with the same pattern as `distribution.test.ts`.

## Pattern 2: BandShareSeries Type in selectors.ts

The new type lives in `selectors.ts` alongside the existing `Summary` interface:

```typescript
// src/state/selectors.ts (additions)

export type { BandShare } from '../core/tierBands.js';

// Convenience: the full per-year series
export type BandShareSeries = BandShare[];
```

The selector converts `ProjectionResult → BandShare[]` and is called in AppShell following the existing memoization pattern:

```typescript
// AppShell.tsx (planned addition)
const bandShares = useMemo(
  () => (rawResult !== null ? deriveBandShares(rawResult.series) : null),
  [rawResult],
);
// Note: uses rawResult (not basis-reinflated result) — shares are basis-invariant (D-12)

const shareOption = useMemo(
  () => (bandShares !== null && rawResult !== null ? selectShareOption(bandShares, rawResult) : null),
  [bandShares, rawResult],
);

const donutOption = useMemo(
  () => (bandShares !== null && rawResult !== null ? selectDonutOption(bandShares, rawResult) : null),
  [bandShares, rawResult],
);
```

**Basis-invariance (D-12):** `deriveBandShares` operates on `rawResult.series` (real basis). Because shares are dimensionless fractions (`bandWealth / totalWealth`), re-inflating both numerator and denominator by the same factor `(1+i)^year` cancels exactly — shares are invariant. The planner MUST use `rawResult` (not the reinflated `result`) as input to `deriveBandShares`. This is the same pattern used for `selectRelPosOption(rawResult)` in the existing AppShell (line 71: "D-08: Chart 3 uses rawResult — rank is real-basis-independent").

## Pattern 3: ECharts 6 — 100%-Stacked Area with User-Position Line Overlay

**Landmine:** In ECharts 6, placing a `line` series in the same `series[]` array as `stack: '100%'` area series causes the line to be included in the normalization calculation, corrupting the 100% stacking. The correct solution is to use a **second y-axis** for the line series, configured as a hidden axis covering [0, 100] (user percentile space, scaled to the chart's 0–100% display range).

```typescript
// selectShareOption: EChartsOption skeleton
{
  grid: { top: 24, right: 16, bottom: 32, left: 48 },
  xAxis: { type: 'value', name: 'Year', ... },
  yAxis: [
    // Index 0: percentage axis for stacked bands (0–100%)
    {
      type: 'value',
      min: 0,
      max: 100,
      axisLabel: { formatter: (v: number) => `${v}%` },
    },
    // Index 1: hidden axis for user position line (0–100 = percentile)
    // userPercentile * 100 maps directly to [0,100] on the hidden axis,
    // which visually aligns with the stacked-area bands' percentage scale
    {
      type: 'value',
      min: 0,
      max: 100,
      show: false,  // hidden — the scale is already represented by yAxis[0]
    },
  ],
  series: [
    // Band series (5 stacked areas) — poorest at bottom (D-09)
    // ECharts renders stack items bottom-to-top in series order,
    // so bottom50 must be series[0], top01 must be series[4].
    { type: 'line', areaStyle: {}, stack: '100%', yAxisIndex: 0, name: 'Bottom 50%', ... },
    { type: 'line', areaStyle: {}, stack: '100%', yAxisIndex: 0, name: '50–90%', ... },
    { type: 'line', areaStyle: {}, stack: '100%', yAxisIndex: 0, name: '90–99%', ... },
    { type: 'line', areaStyle: {}, stack: '100%', yAxisIndex: 0, name: '99–99.9%', ... },
    { type: 'line', areaStyle: {}, stack: '100%', yAxisIndex: 0, name: 'Top 0.1%', ... },
    // User position overlay — NOT stacked, uses hidden yAxis[1]
    {
      type: 'line',
      yAxisIndex: 1,  // CRITICAL: separate axis prevents stack contamination
      name: 'Your position',
      data: result.series.map((s) => [s.year, s.userPercentile * 100]),
      lineStyle: { color: COLORS.user, width: 3.5, type: 'dashed' },  // dashed to distinguish
      showSymbol: false,
      endLabel: { show: true, formatter: () => 'You', color: COLORS.user, ... },
    },
  ],
}
```

**Data format for stacked-area series:** ECharts `stack: '100%'` with `type: 'line'` + `areaStyle: {}` expects `data` as `[xValue, yValue]` pairs where `yValue` is the raw (non-normalized) value — ECharts normalizes to 100% internally. Feed the raw band share fractions (0–1 range) multiplied by 100 to give percentage values, or feed raw values (0–1) and rely on ECharts normalization. Both work; multiplying by 100 gives cleaner tooltip values.

**D-06 user-position mapping onto the cumulative-share axis:** `userPercentile` in `YearSnapshot` is a [0,1] CDF value. Multiplied by 100 it gives [0, 100] — the same range as the stacked-band display (which is also 0–100%). At `userPercentile = 0.75`, the user line sits at the 75th percentile mark, which visually crosses through the boundary between the Bottom-50%+50-90% bands and the 90%+ bands. This is correct and communicates "the user sits at the 75th percentile of the distribution" mapped onto the share axis. The two axes [yAxis[0] = share%, yAxis[1] = percentile%] have identical [0,100] domains, so the hidden axis trick is visually transparent. [ASSUMED: this is the intended D-06 mapping — needs planner confirmation if the intent is something else]

**ECharts 6 `stack: '100%'` verified behavior:** In ECharts 6.0.0, `stack: '100%'` on `line` series with `areaStyle` normalizes each x-point so all stacked values sum to 100%. Series order in the array controls bottom-to-top render order. [VERIFIED: ECharts 6.0.0 installed at node_modules/echarts/package.json]

## Pattern 4: ECharts 6 — Donut Chart with Highlighted Slice

The donut (end-of-horizon snapshot) uses `type: 'pie'` with `radius: ['40%', '70%']` for the donut hole. The center label displaying the top-set concentration uses `graphic` element or ECharts' `pie` center-text feature.

```typescript
// selectDonutOption: EChartsOption skeleton
{
  graphic: [{
    type: 'text',
    left: 'center',
    top: 'middle',
    style: {
      text: `Top ${(100 - lastSnap.topSetPercentile * 100).toFixed(1)}%\nhold ≥50%\n(year ${lastSnap.year})`,
      textAlign: 'center',
      fontSize: 13,
      fill: '#475569',  // slate-600
    },
  }],
  series: [{
    type: 'pie',
    radius: ['40%', '70%'],
    // D-09: band order clockwise from 12, poorest first
    // ECharts pie starts at the top (12 o'clock) by default; startAngle: 90 confirms this
    startAngle: 90,
    data: [
      { name: 'Bottom 50%', value: lastBandShare.bottom50, itemStyle: { color: COLORS.median } },
      { name: '50–90%',     value: lastBandShare.band50to90,  itemStyle: { color: COLORS.top10 } },
      { name: '90–99%',     value: lastBandShare.band90to99,  itemStyle: { color: COLORS.top1 } },
      { name: '99–99.9%',   value: lastBandShare.band99to999, itemStyle: { color: COLORS.top01 } },
      { name: 'Top 0.1%',   value: lastBandShare.top01,       itemStyle: { color: COLORS.user } },
    ],
    // D-07: highlight the band containing the user at the final year
    // Use 'emphasis' on the matching data item, not 'selected' (deprecated for pie in ECharts 6)
    emphasis: {
      // Applied to all slices as the default; the user's band gets additional itemStyle override
    },
    label: { show: true, formatter: '{b}: {d}%' },
  }],
}
```

**D-07 "your band" outline — ECharts 6 API:** The user's band is identified by computing which of the 5 bands contains `lastSnap.userPercentile`. The correct ECharts 6 mechanism is NOT `selected: true` (that is a pre-ECharts-5 API, deprecated for pie type). The correct mechanism is:

1. Set `emphasis.itemStyle.borderColor + borderWidth` on the matching data item directly:

```typescript
// Identify which band the user falls in at the final year
function userBandIndex(userPercentile: number): number {
  if (userPercentile < 0.5) return 0;   // Bottom 50%
  if (userPercentile < 0.9) return 1;   // 50–90%
  if (userPercentile < 0.99) return 2;  // 90–99%
  if (userPercentile < 0.999) return 3; // 99–99.9%
  return 4;                              // Top 0.1%
}

// In the donut data array, mark the user's band:
data[userBandIdx].itemStyle = {
  ...data[userBandIdx].itemStyle,
  borderColor: '#1E293B',  // slate-800 — neutral outline, no red/green
  borderWidth: 3,
};
// Or use label emphasis:
data[userBandIdx].label = { show: true, fontWeight: 600 };
```

2. Alternatively, use `selectedMode: 'single'` + `selected: true` on the data item. This is supported in ECharts 6 for pie type and causes the slice to "pop out" visually. However, "pop out" may feel alarming/evaluative — a simple border outline (borderColor/borderWidth) is more neutral and aligns with D-04 palette restraint.

**Recommendation:** Use `itemStyle.borderColor + borderWidth` on the matching data item (not `selected: true`) for a neutral, non-animated highlight. [ASSUMED: ECharts 6 pie `itemStyle.borderColor` on a data item overrides at the data level — standard ECharts item-level override]

## Pattern 6: D-16 Neutrality Style Guide Rule

### Structural template (mirrors D-15 in Section 6)

The new rule goes in `docs/NEUTRALITY-STYLE-GUIDE.md` as **Section 7 — D-16 Share-of-Economy Neutral Disclosure Rule**.

**Mirror structure:**
- Section heading: matches "Section 6 — D-15 Rank-Delta Neutral Disclosure Rule" in format
- Seeded date, Phase 5 gate statement
- Context paragraph: why the caption is needed (shares can move in one direction while absolute wealth grows in all bands)
- Required caption template (verbatim text, Phase 5 checks equality)
- Constraints: visible DOM `<p>` element, not collapsible, on/near both charts

## Common Pitfalls

### Pitfall 1: Line Series Inside `stack: '100%'` Corrupts Normalization

**What goes wrong:** Adding the user-position line series to the same `series[]` array as the stacked areas without `yAxisIndex` separation causes ECharts to include the line's values in the 100% normalization. The stacked bands will not sum to 100% visually.

**Why it happens:** ECharts `stack: '100%'` applies to all series that share the same `stack` key AND the same `yAxisIndex`. If the line series lacks an explicit `yAxisIndex`, it defaults to 0 (same as the areas) and ECharts includes it in the normalization.

**How to avoid:** Give the user-position line `yAxisIndex: 1` pointing to a second y-axis configured with `show: false`. The stacked areas use `yAxisIndex: 0` (explicit).

**Warning signs:** The stacked areas do not reach the top of the chart (fail to hit 100% at every x-point).

### Pitfall 2: Calibration Fallback Not Mirrored in deriveBandShares

**What goes wrong:** The engine falls back from `calibrateCurve` to `shiftScaleCurve` for evolved-distribution edge cases. If `deriveBandShares` calls `calibrateCurve` without the same fallback, it will throw at the same edge cases the engine handles gracefully.

**Why it happens:** After many years of endogenous re-calibration, the top01/top1 ratio can exceed 10, triggering the CR-02 alpha<=1 guard in `calibrateCurve`. The engine already handles this via `try/catch → shiftScaleCurve`. `deriveBandShares` must mirror this.

**How to avoid:** In `deriveBandShares`, wrap `calibrateCurve` in a `try/catch`. On failure, reconstruct the curve using the same `shiftScaleCurve` approach the engine uses, or return the prior year's band shares (or a null/degenerate result). The AppShell null-guard will prevent rendering if the result is null.

**Warning signs:** The stacked-area chart disappears or shows NaN at later years in long-horizon projections with high drag settings.

### Pitfall 3: Band Fractions Not Summing to Exactly 1.0

**What goes wrong:** Floating-point accumulation from five `cumulativeShareFromTop` calls produces a sum of `0.9999999...` or `1.0000001...`. If the selector normalizes these values for ECharts, a tiny off-by-epsilon can cause ECharts to display a visual gap or overflow at the top of the stacked area.

**Why it happens:** `cumulativeShareFromTop` is a closed-form formula using floating-point arithmetic. The five differences are mathematically exact but not bitwise exact.

**How to avoid:** Normalize the five band values to sum to exactly 1.0 before passing to ECharts: `const total = sum(bands); return bands.map(b => b / total)`. This is safe because if the raw values are within 1e-6 of 1.0 (DIST_TOL), dividing by the sum corrects the epsilon without distorting the display. Add a test asserting `|sum - 1.0| < 1e-6` on the raw values.

**Warning signs:** A white gap or overflow at the top of the stacked-area chart at certain years.

### Pitfall 4: Donut `selected: true` (Deprecated Pie Highlight API)

**What goes wrong:** Using `selected: true` on a pie data item in ECharts 6 does not consistently produce the desired "your band" visual. The property is inherited from ECharts 4 and its behavior on `pie` type changed in ECharts 5+.

**Why it happens:** The ECharts 6 API for pie slice visual state uses `emphasis` + `itemStyle.borderColor/borderWidth` at the data-item level for a static persistent outline, whereas `selected: true` triggers an animation that may or may not be persistent depending on `selectedMode`.

**How to avoid:** Set `itemStyle.borderColor` and `itemStyle.borderWidth` directly on the matching data object. This is a static, non-animated visual that persists without user interaction.

**Warning signs:** The "your band" slice only shows the outline on hover, or not at all, or produces an unexpected animation.

### Pitfall 5: Basis-Reinflated Result Passed to deriveBandShares

**What goes wrong:** Passing `result` (the reinflated result from `selectReinflated`) instead of `rawResult` to `deriveBandShares` produces nominally-inflated anchor values. `calibrateCurve` reconstructed from inflated anchors produces different curve parameters. Because inflation is uniform across all wealth levels, the CDF shape is unchanged and band shares are the same — but this only holds exactly when ALL anchor values are inflated by the same factor. Due to the non-linear lognormal+Pareto curve, inflating anchor points by year-dependent factors may introduce small inconsistencies.

**Why it happens:** `selectReinflated` scales anchor wealth values by `(1+i)^year`, but the lognormal+Pareto curve parameters are non-linear in the anchor values (mu = ln(median), sigma depends on ln(top10/median), alpha depends on ln(top01/top1)). The log-ratio `ln(top01/top1)` is invariant under uniform multiplicative inflation (the factor cancels), so alpha is actually invariant. Mu shifts by `ln(1+i)^year` and sigma is also invariant. So the curve shape is invariant under uniform real-to-nominal scaling — but the code path is more complex than needed.

**How to avoid:** Always pass `rawResult` (real basis) to `deriveBandShares`. The D-12 basis-invariance test must assert that both real and nominal inputs produce byte-identical band shares. The test verifies the invariant is maintained regardless of implementation path.

**Warning signs:** The basis-invariance test in D-12 fails.

## Code Examples

### Computing one year's band shares (pure function sketch)

```typescript
// src/core/tierBands.ts
// Source: [ASSUMED — planned implementation based on cumulativeShareFromTop from distribution.ts]

import { calibrateCurve, cumulativeShareFromTop, type Curve } from './distribution.js';
import type { YearSnapshot } from './types.js';

export interface BandShare {
  year: number;
  bottom50: number;    // fraction held by population [0, 0.5)
  band50to90: number;  // fraction held by population [0.5, 0.9)
  band90to99: number;  // fraction held by population [0.9, 0.99)
  band99to999: number; // fraction held by population [0.99, 0.999)
  top01: number;       // fraction held by population [0.999, 1]
}

function bandsFromCurve(curve: Curve, year: number): BandShare {
  const s50  = cumulativeShareFromTop(curve, 0.5);    // share above p50
  const s90  = cumulativeShareFromTop(curve, 0.9);    // share above p90
  const s99  = cumulativeShareFromTop(curve, 0.99);   // share above p99
  const s999 = cumulativeShareFromTop(curve, 0.999);  // share above p99.9

  const raw = {
    year,
    bottom50:    1 - s50,
    band50to90:  s50 - s90,
    band90to99:  s90 - s99,
    band99to999: s99 - s999,
    top01:       s999,
  };

  // Normalize to exactly 1.0 (floating-point correction, Pitfall 3)
  const total = raw.bottom50 + raw.band50to90 + raw.band90to99 + raw.band99to999 + raw.top01;
  const f = total > 0 ? 1 / total : 1;
  return {
    year,
    bottom50:    raw.bottom50    * f,
    band50to90:  raw.band50to90  * f,
    band90to99:  raw.band90to99  * f,
    band99to999: raw.band99to999 * f,
    top01:       raw.top01       * f,
  };
}
```

export function selectShareOption(
