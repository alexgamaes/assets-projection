# Phase 04.1: Code Review Report

**Reviewed:** 2026-05-16
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

Reviewed the VIZ-07 tier-share visualization slice: the `deriveBandShares` engine
(`tierBands.ts`), the two new selectors (`selectShareOption`, `selectDonutOption`,
`SHARE_CAPTION`), the two thin chart wrappers, and AppShell wiring.

The core Lorenz-band math is sound and well-tested (band-sum, basis-invariance,
Pareto fixture, fallback no-throw). The defects cluster around the **interaction
between the calibration-failure fallback path and the donut center label**, which
together can render a chart that visually contradicts its own caption — a
correctness *and* neutrality problem given the project's analytical-neutrality
constraint. Secondary issues concern display-layer normalization loss and a
hardcoded factual claim ("hold ≥50%") that is not guaranteed true for the value
it is paired with.

## Critical Issues

### CR-01: Donut center label contradicts the rendered slices in the calibration-failure fallback path

**File:** `src/state/selectors.ts:569-598`, interacting with `src/core/tierBands.ts:202-219`

**Issue:** `deriveBandShares` has two fallback branches when `calibrateCurve`
throws (CR-02 alpha ≤ 1 in evolved distributions):
- year 0 → `degenerateBand` = all five bands `0.2` (uniform).
- year ≥ 1 → carry forward the *previous* year's band values.

`selectDonutOption` reads the final-year `BandShare` (`lb`) for the slices, but
derives the center label from a completely independent field —
`last.topSetPercentile` — taken straight off `result.series[last]`, which is
**never recomputed in the fallback**. When the final year falls into the fallback
path (a realistic scenario: the threat model explicitly anticipates evolved
top01/top1 ratios producing alpha ≤ 1 in *later* years, exactly the years the
donut visualizes), the donut renders five equal 20% slices (or stale
carried-forward shares) while the center text asserts `Top {topPct}% hold ≥50%`
computed from an unrelated, possibly extreme `topSetPercentile`. The chart's two
primary visual elements then state mutually contradictory things, and the center
claim is not derivable from what the donut shows. This is incorrect output and a
neutrality violation (the tool presents an unsupported factual claim).

**Fix:** Derive the center-label percentile from the *same* band data the donut
renders, or suppress/replace the quantitative claim when the final-year band came
from the fallback path. Tag fallback entries so the donut can detect them:

```ts
// tierBands.ts — mark fallback-origin entries
export interface BandShare {
  year: number;
  bottom50: number; band50to90: number; band90to99: number;
  band99to999: number; top01: number;
  /** true when this entry was synthesized by the calibration-failure fallback. */
  degraded?: boolean;
}
// degenerateBand(): return { ...bands, degraded: true }
// carry-forward: result.push({ ...prev, year, degraded: true })
```

```ts
// selectDonutOption — derive the center claim from the bands actually drawn,
// and avoid the hardcoded "≥50%" assertion when degraded.
const cum = lb.top01 + lb.band99to999 + lb.band90to99; // top 10% share, etc.
const centerText = lb.degraded
  ? `Calibration unavailable\n(year ${last.year})`
  : `Top ${topPct}%\nhold ≥50%\n(year ${last.year})`;
```

## Warnings

### WR-01: Hardcoded "hold ≥50%" claim is not guaranteed true for the paired percentile

**File:** `src/state/selectors.ts:597-598`

**Issue:** `topPct = (100 - last.topSetPercentile * 100).toFixed(1)` and the label
is fixed text `Top ${topPct}%\nhold ≥50%`. `dynamicTopSetPercentile` (the source
of `topSetPercentile`) explicitly clamps to `hi = 0.9999` when the top (1−hi)
fraction already holds *more* than 50% of wealth ("deliberate modeling clamp").
In that clamped case the displayed group holds *strictly more* than 50%, so "hold
≥50%" is technically true but understated; conversely no invariant in the
reviewed code ties the rounded `topPct` back to the exact 50% crossing, so the
pairing of an arbitrary rounded percentile with the literal "≥50%" is asserted
rather than computed. For a correctness-first, source-citing tool this is fragile.

**Fix:** Either compute and display the *actual* cumulative share the top
`topPct%` holds (so the number and the claim are consistent by construction), or
phrase the label so it cannot become false (e.g. `Top ${topPct}% (≈50% of total)`),
and add a unit test asserting the displayed percentile reproduces the 50% crossing
for a known fixture.

### WR-02: Per-slice independent rounding discards the D-01 exact-sum normalization

**File:** `src/state/selectors.ts:579-583`

**Issue:** `deriveBandShares` deliberately normalizes the five bands to sum to
exactly 1.0 (Pitfall 3 float-sum correction, heavily tested). `selectDonutOption`
then rounds each slice independently with `+(x*100).toFixed(2)`, so the five
displayed values generally no longer sum to 100. ECharts recomputes `{d}%` from
these independently-rounded values, so the donut percentages can sum to 99.99 /
100.01 and the largest-remainder consistency the engine guarantees is lost at the
display boundary. Minor numerically, but it silently defeats a property the
engine and its test suite went to lengths to guarantee.

**Fix:** Pass full-precision values to ECharts and let the label formatter round
for display, or apply largest-remainder rounding so the five rendered values sum
to exactly 100.

### WR-03: `selectShareOption` user line and `selectDonutOption` slices read different result objects than the bands when basis = nominal

**File:** `src/ui/AppShell.tsx:82-93`, `src/state/selectors.ts:534`

**Issue:** AppShell intentionally feeds `rawResult` (real basis) to
`deriveBandShares`, `selectShareOption`, and `selectDonutOption` (D-12
basis-invariance). That is correct for the band fractions. However
`selectShareOption` plots the user-position line from
`result.series.map((s) => [s.year, s.userPercentile * 100])` where `result` here
is the *rawResult* passed in — `userPercentile` is unitless so this is fine — but
the surrounding AppShell prose ("Shares are identical in real and nominal terms")
plus the use of `rawResult` while every other chart uses re-inflated `result`
makes the basis contract easy to break on future edits. There is no test
asserting `selectShareOption`'s user line equals `userPercentile*100` for a
nominal-basis input, so a regression that accidentally swaps `rawResult`→`result`
here would be silent.

**Fix:** Add a regression test: `selectShareOption(bands, reinflatedNominal)`
series[5] data must equal `series[5]` of `selectShareOption(bands, real)`
(userPercentile is basis-invariant). Document the rawResult requirement at the
selector signature, not only in AppShell.

### WR-04: `deriveBandShares` swallows all errors with a bare `catch {}`, masking non-calibration failures

**File:** `src/core/tierBands.ts:206-219`

**Issue:** The `catch` block assumes every thrown error is the CR-02
`alpha ≤ 1` calibration guard and silently substitutes a uniform/carried-forward
band. Any *other* failure (e.g. a future bug in `computeBandFromCurve`,
`cumulativeShareFromTop` throwing, a malformed `snap.anchorWealth` producing NaN
that surfaces as a throw) is indistinguishable and silently produces plausible-
looking-but-wrong bands with zero diagnostic. For a correctness-first model this
is a dangerous swallow.

**Fix:** Narrow the catch — inspect the error and only apply the fallback for the
known calibration guard; rethrow or at minimum surface unexpected errors:

```ts
} catch (err) {
  if (!isCalibrationGuardError(err)) throw err; // don't mask unknown bugs
  // ... existing fallback ...
}
```

### WR-05: `degenerateBand` uniform 0.2 split is a silently wrong distribution, not a neutral failure state

**File:** `src/core/tierBands.ts:122-131`

**Issue:** On year-0 calibration failure the function emits a *valid-looking*
egalitarian distribution (every tier holds exactly 20%). Downstream this renders
as a real chart with no indication the data is synthetic, directly contradicting
the project's "don't assume stuff / data integrity" and neutrality constraints —
it fabricates an equal-distribution narrative. The sum-to-1.0 test passes, hiding
the problem.

**Fix:** Couple with CR-01's `degraded` flag so the UI can render an explicit
"unavailable" state instead of a fabricated equal split, rather than emitting
plausible numbers.

## Info

### IN-01: `selectShareOption` band data array recomputed; `result` param only used for tooltip dataIndex and user line

**File:** `src/state/selectors.ts:440-548`

**Issue:** `selectShareOption` takes both `bandSeries` and `result`; `result` is
used only for the tooltip year lookup and the user line. The tooltip resolves
`snap = result.series[dataIndex]` but band x-values come from `bandSeries[].year`.
If `bandSeries.length !== result.series.length` (cannot happen today, but the
contract is implicit) the tooltip year and band index silently desynchronize.
Consider asserting/`console`-free invariant or documenting the length equality
the two args must satisfy.

### IN-02: `DonutChart.tsx` and `TierShareChart.tsx` are byte-identical except component name

**File:** `src/viz/DonutChart.tsx:1-28`, `src/viz/TierShareChart.tsx:1-28`

**Issue:** The two wrappers are exact duplicates (same markup, props, styles,
comments). Pure code duplication; a shared `<CaptionedChart>` would remove it.
Not a correctness issue.

**Fix:** Extract a single `CaptionedEChart({ option, caption, style })` and have
both names alias it, or replace both call sites with the shared component.

### IN-03: Magic color-to-band mapping reuses semantically-unrelated palette keys

**File:** `src/state/selectors.ts:454-458`, `579-583`

**Issue:** Band slices reuse `COLORS.median/top10/top1/top01/user` for
*population bands* that do not correspond to those tiers (e.g. "Top 0.1%" band is
colored `COLORS.user`, "Bottom 50%" is `COLORS.median`). This is intentional per
D-04 ("existing COLORS constants only") but the key names actively mislead a
future maintainer into thinking the color encodes the same tier. A dedicated
`BAND_COLORS` map with band-named keys would prevent accidental misuse.
